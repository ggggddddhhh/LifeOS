## 架构限制（明确记录，本轮不解决）

**慢网络下同步 Calendar 批量写入存在吞吐上限。**
全链路为同步 HTTP：浏览器 → Next.js（undici fetch ~300s headersTimeout 硬顶）→
agent → Google（无代理下单次 40–60s，读可通、写常超时）。N 个事件的确认串行
耗时 ≈ 60s + N×(40~60)s，**N≈4 即触顶**——预算调参无法根治（发现 #4 实测：
180s/270s/304s 三次尝试均在顶内失败，agent 后台仍会写完且幂等不重复，但 TS
收不到结果无法落库，形成"日历有事件、DB 无记录"漂移，需再次确认收敛——
恢复路径已验证可用）。

后续候选项（新功能，需立项）：确认后转后台队列执行 + 完成回写 + 状态轮询；
或分批确认（每批 ≤3 事件）。当前运维建议：慢网络下事件较多的确认失败时，
直接再次点击确认即可收敛（幂等安全），无需手工修复。
