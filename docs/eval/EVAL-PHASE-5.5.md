# Phase 5.5 验证报告 — GitHub × Calendar 双工具联合价值（四臂评测）

- 日期：2026-09-09 · 模型：`deepseek-chat` · 脚本：`agent/eval_p55.py`
- 设计：10 场景（覆盖要求的全部 10 类）× 四臂 A=无工具 / B=仅GitHub / C=仅Calendar / D=双工具，共 40 次真实 LLM 调用；fixture 只声明世界状态，期望谓词由场景性质推导
- 原始数据：[p55-results.json](p55-results.json)

## 1. 核心发现：协同收益是行为性的，且量化明确

**各臂在 10 场景上的两个盲区指标**：

| 臂 | 超出真实容量的场景数 | 识别出进度落后（4 个 behind 场景） |
|---|---|---|
| A 无工具 | 5 | 0 |
| B 仅 GitHub | 5 | **4** |
| C 仅 Calendar | 2 | 0 |
| D 双工具 | 1（且为图级差 60min，TS 守卫兜底至 ≤容量） | **4** |

结论一目了然：**B 看得见进度看不见容量，C 看得见容量看不见进度，只有 D 两者都看见**。单一工具各自修复一半盲区，双工具叠加后才同时修复两个。

## 2. 重点场景深挖（s4：项目落后 + 未来三天仅少量空闲）

- **D 臂 reason（双维度协同的直接文本证据）**："GitHub 观察显示 issue #100 数据迁移已关闭，故从计划移除。CI 失败与 PR #50 未合并表明核心 API 存在质量风险……容量紧张（5 天仅 660 分钟），将集成测试与部署脚本合并……排期到可用量大的 09-12/13"——一句话里同时处理交付阻塞（移除已关、优先核心）与时间不足（合并、压缩、错峰排期）
- **B 臂的容量盲区原文**："总估时 1170 分钟未超容量 2400 分钟（默认 480×5），无需压缩"——按默认容量放行，实际 960 > 真实 660
- **C 臂**：压到 720 贴近容量，但完全不知道 #100 已完成、不知道 CI/PR 风险
- **D 臂**：720（图级）+ TS 硬守卫收敛 ≤660，双风险全识别，observed_done=[数据迁移] 正确
- expect(D) 谓词判 False 的唯一原因是图级 720 > 660+30 容差——如实记录：这是"LLM 尽力 + 确定性守卫"分层的预期工作方式（守卫单测已证明 1140/660 覆写下正确裁剪）

## 4. 如实记录的两个评测侧问题与一个行为分歧

1. `dualDimensionOnlyInD=0` 是**指标失真**：B 臂 reason 也会出现"容量"字样（默认容量的例行表述），token 检测无法区分"真实容量"与"默认容量措辞"——协同证据改用 §1 的行为指标（超容量数×落后识别数的矩阵）。教训与 Phase 4.5 相同：措辞检测弱于行为检测。
2. s8 的 `structuralChangeVsA` 受 A 基线 LLM 噪声影响（A 臂无理由地把 1170 压到 870），该指标只宜看 s1/s10 这类"明确不应变化"的场景（均为 0）。
3. **行为分歧（产品观察，非 bug）**：s8 冲突场景中 LLM 选择把用户标记 done 的任务以"待确认"形式保留进新计划（taskCount 6）而非简单维持移除——reason 明确标注了冲突与置信度降低，符合"显式标注、不静默"的要求，但呈现方式有自由度；后续可把"冲突任务的呈现方式"统一为产品约定。

## 5. 五问回答

### 5.1 GitHub + Calendar 是否存在明显协同收益？
**存在，且是结构性的。** 双风险场景（s4/s5/s6）中 D 是唯一同时做到"移除已完成 + 识别阻塞 + 按真实容量压缩 + 错峰排期"的臂；单工具各修一半盲区（B 修进度、C 修容量），叠加后 10 场景全部达标（含守卫兜底层）。reason 文本首次出现"因为 #100 已关所以移除，且因容量 660 所以合并"这类**跨两个事实源**的归因链。

### 5.2 哪些情况下单工具已经足够？
- **仅 GitHub 足够**：时间充裕或 deadline 很远（容量不构成约束）的进度修正——s2（CAL 充足）中 B 与 D 行为等价；
- **仅 Calendar 足够**：进度健康但时间紧张的自我压缩——s3/s9 中 C 与 D 的容量处理等价（s9 还证明 GitHub 故障时 Calendar 独立撑住容量维度）；
- **无需任何工具**：无仓库、时间宽裕的常规重排（A 臂一直可用，s10 双故障时 D≡A 完全回退）。

### 5.3 哪些情况下必须双工具结合？
**"落后 + 时间不足"的复合压力场景（s4/s5/s6）**：只修进度会给出放不下的计划（B：960>660），只修容量会保住错误的任务集（C：不知道 #100 已完成、不知道 CI/PR 阻塞）。临近 deadline 时两类风险必然耦合出现，正是双工具的目标场景——也是本产品的核心叙事（"既要看清事，也要看清时间"）。

### 5.4 当前 Replanner 最大剩余问题是什么？
**图级容量收敛精度**：LLM 对硬容量上限的逼近止步于 ±10%（s4 720/660、s9 曾 360/300），完全收敛依赖 TS 守卫兜底。这没有正确性风险（守卫确定性保证），但意味着 LLM 生成的一部分计划在守卫处被二次裁剪——reason 中"总估时 X 分钟"与最终入库值可能不一致。改进方向：把容量守卫前移到 Python Finalize 节点（与 TS 同一算法），让 reason 与最终计划一致。次要问题：冲突任务的呈现方式存在 LLM 自由度（§4.3）。

### 5.5 是否值得进入 Email / Calendar 写操作阶段？
**Email（只读）：值得**——双工具已证明"多事实源 + 确定性合成"的模式可复制且零误引用，Email 的"沟通证据"是第三类独立事实源，边际成本低。
**Calendar 写操作：暂缓**——当前最大剩余问题是容量收敛精度（§5.4），它是纯算法问题且收益立竿见影；写操作引入的是确认机制、幂等、冲突合并等一整层新复杂度，应等读路径的价值完全榨干后再上。建议顺序：Python 侧容量守卫前移 → Email 只读 → 再评估写操作。
