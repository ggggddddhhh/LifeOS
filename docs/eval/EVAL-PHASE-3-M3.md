## 2. 迁移差异记录（按要求 #8，未修改任何一侧）

1. **Prompt payload 不完全相同**：Python 的 Plan/Replan 节点在 user 消息里注入 `analysis`（daysLeft、openCount、openTotalMinutes、capacityMinutes、overloaded）；TS 本地路径只发原始输入。证据：python 的 reason 会出现"原计划 2820 分钟严重超载"这类只有 analysis 才提供的精确数字。
   - 影响：python 在超载场景下压缩更果断（雅思延期 6→4，探针复核理由充分）；也可能是极简输出偏多的诱因之一。
   - 处置：记录为已知迁移差异。对齐方向（把 analysis 注入 TS 或从 python 移除）留待 M4 决策，不在评测中偷偷改。
2. **极简输出的结构性下限一致**（≥1 任务 + 非空 reason 即通过），两侧 acceptance 相同。

## 3. 极简输出专项统计（要求 #6）

- 出现频率：python 2/27（7.4%），均为「雅思·延期」场景（6 个未完成任务 → 2 任务 / 1 任务）；local 0/27。
- 事后探针复核（同场景再打 2 次）：得到的是 4 任务计划，理由引用容量数据、放弃项明确（"放弃听力与阅读专项训练，合并口语与写作为每日综合冲刺"）——质量良好。
- 可用性判断：1-2 任务的计划**结构可用**（非空 reason、合法字段、看板可展示），但颗粒度偏粗；产品侧已有护栏兜底——TS 的 `enforceTimeBudget`/diff 展示不受影响，且此场景本来就是"严重超载必须大砍"的极端输入。判定：不影响实际可用性，但值得在 M4 后持续观察（若换模型后频率上升，可在 python Validate 加"任务数≥3 软提示重试"——已有重试机制可承载）。

## 4. 五个问题的回答

1. **Python 路径质量是否不低于 local？** 是。所有合格率指标持平（100%），膨胀/泄漏/依赖/日期/重复全部为零；仅 Planner 超载率 3.3% vs 0%（超载 17 分钟/天，量级可忽略）与极简输出 7.4% vs 0%（见 §3，判定不影响可用性）。
2. **是否引入明显稳定性问题？** 否。0 请求失败、0 重试触发、graph 无死循环（M1 已结构保证），延迟分布与 local 一致。
3. **LangGraph 当前是否带来实际收益？** 编排收益目前是"结构性"而非"质量性"：Validate-重试安全网已就位（本轮未触发）、Analyze 注入使超载场景的砍范围决策更有依据（reason 质量可见提升）、节点化为 Phase 4 工具调用/主动感知提供了扩展点。质量指标本身与单次调用路径持平——符合预期（M3 约束下 graph 只有 4 个节点、无工具）。
4. **新增延迟是否可接受？** 可接受。端到端 avg 差 +7ms（3343 vs 3336），P95 反而略低（噪声）；HTTP+图开销 ~50ms 完全被 LLM 延迟（3-5s）淹没。
5. **是否建议 M4 将默认切到 auto？** **建议切换**。条件全部满足：质量持平、稳定性持平、延迟无感知差异、降级链经 M2 四场景冒烟验证。auto 模式下 Python 故障自动回落 local，用户无感。

## 5. 遗留观察

- 迁移差异 §2.1（analysis 注入不对称）建议在 M4 明确决策：倾向保留 python 的 analysis 注入（数据更好），并接受两侧 fallback 路径行为有此细微差异。
- 极简输出与 planner 轻微超载均与 LLM 非确定性同量级，3 轮样本不足以定论，M4 后建议按月复跑 `test:m3` 观察。
