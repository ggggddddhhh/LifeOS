## 2. 评测基础设施自身的三个 bug（已修，非产品问题）

1. stub 用 `"closed" in url` 判断查询参数，被场景名 `scn03_closed_done` 中的 "closed" 误触发——改为精确匹配 `state=closed`
2. 我的三处 ground truth 写错：PR 不参与 issue 匹配（设计如此，PR 走 signals 且 reason 已正确引用）、done 任务走 conflicts 通道不进 matches、"发版说明/物料"本就不该匹配
3. 检测器误报：cited/fabricated 正则把任务标题里的 "CI/PR" 和常规 replan 用语"合并"当成 GitHub 引用——收紧为 `#\d+|issue|PR|CI|GitHub|仓库`

教训已固化：**指标异常先查测量仪器，再下产品结论**——第一次运行 5 个"漏匹配"全部出在评测侧。

## 3. 意外发现（记录，不处理）

scn11（中英标题）中确定性匹配器正确地零匹配，但 LLM 在 reason 里**自行完成了跨语言语义对应**（"抽取界面文案 ↔ Extract UI strings"）且陈述准确、未影响计划。这 technically 违反 prompt 的"仅 matches 可用"约束（虽然只用于评述）。含义：LLM 的语义匹配能力超过我们的确定性匹配器，跨语言场景的匹配上限在 LLM 侧；风险是未经置信度控制的自行匹配，后续若开放需给它同样的置信度框架。

## 4. 五问回答

### 4.1 GitHub Tool 是否显著改善 Replan？
**显著。** 无 Context 时 Agent 对"已完成/计划外/阻塞"完全失明（A 臂在这三类场景无法产生任何相应动作）；有 Context 后：该移除的移除（3 处）、该新增的新增且说明放弃了什么（2 处）、该裁剪的裁剪（1 处）、冲突显式上报而非静默覆盖——且**零误伤**（无信号场景计划逐字节不变）。价值不仅在外部数据本身，更在 reason 从"容量计算"升级为"可归因的事实推理"。

### 4.2 哪类 GitHub 信号最有价值？
排序：**Issue 关闭事件（observed_done）> 计划外 open issue > CI 失败 > PR 滞留**。前者直接修正状态失真（用户最不自觉的偏差）；计划外 issue 补盲区；CI/PR 更多是风险解释因子（本轮未触发结构变化，但驱动了 behind 判定与优先级论述）。

### 4.3 哪类匹配最容易误判？
本轮实测零误判，但风险排序明确：**①跨语言标题**（确定性匹配器直接放弃，靠 LLM 自行匹配——未经置信度控制，见 §3）；**②"相似但不同义"中文短标题**（"部署上线 vs 部署文档编写"靠共享词较少才幸免，若共享更多词元 Jaccard 可能虚高）；③子串匹配的边界（"实现登录"⊂"实现登录权限重构"会以 0.75 判匹配，语义可能已漂移）。observed_done 的 ≥0.75 门槛挡住了大部分风险，但建议后续给 0.75 档加"需用户确认"标记。

### 4.4 是否达到继续增加第二个 Tool 的标准？
**达到。** 准入判据全部满足：工具可靠性（0 匹配错误、0 误完成、0 干扰、降级 3/3）、价值可证（4/12 结构性改善 + 解释质量质变）、延迟可接受（+0.5s 本地 / 2-3s 公网）、失败安全（从未阻断 graph）。模式（只读客户端+事实 Schema+确定性分析+降级）已被验证可复制。

### 4.5 下一工具选 Calendar 还是 Email？
**Email（只读）。** 理由：①与 GitHub 同为"被动观察"型，可完全复用只读模式与确认哲学，日历是"双向承诺"型，天然需要写操作与确认机制，复杂度跳档；②Email 提供"时间投入证据"（与谁沟通、确认了什么、阻塞在哪），与 GitHub 的"交付状态证据"正交互补，直接喂给 Progress Analysis 的"用户实际在做什么"；③Calendar 的核心价值（时间预算冲突检测）依赖 Phase 2 预算条的深化，属后续组合。
