## 3. 发现的问题与修复（均已修复并有测试覆盖）

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | LLM 端点不可用时用户看到裸 `fetch failed` | 网络层异常未包装 | `OpenAiCompatClient` 统一包装为 `LLM 请求失败（网络错误）: …` |
| 2 | 所有任务已完成后 Replan，LLM 凭空发明新任务 | 无未完成任务时仍调用 LLM | 路由层短路返回 400"所有任务已完成，无需重新计划" |
| 3 | LLM 返回重复任务不会被拦截 | normalize 层无去重 | 归一化标题去重（大小写/空白/标点） |
| 4 | 延期场景 Replan 给出日均 510 分钟（8.5h/天）排期 | prompt 无容量约束 | REPLANNER prompt 加入硬约束：总估时 ≤ 剩余天数×480 分钟，放不下必须合并或砍任务并说明 |

修复后复测：单测 21/21、评测 40/40、build 通过。

## 4. 边界情况结论

- 琐碎目标（"买菜"）：正常拆解不过度膨胀；模糊目标（无 deadline）：可拆解
- deadline 已过/仅剩 1 天：不崩溃，给出聚焦冲刺计划
- 截断 JSON、多代码块、前后噪音、带注释 JSON、tasks 非数组：extractJson 全部安全处理（解析或抛错，无半成品）
- 字段类型混乱（数字标题、null 估时、中文优先级）：安全回退默认值
- 无 Key：自动降级 mock，闭环可用（生产安全网）

## 5. 遗留观察（不阻塞 Phase 2）

1. **estMinutes 语义二义**：习惯型任务（"建立每周 4 次运动习惯" 240min）的估时是"投入成本"而非"持续时间"。Phase 2 时间预算需区分。
2. **范围蔓延**：时间充裕时 Replanner 会主动加任务（回归测试、SEO）。Phase 2 计划版本应展示 diff 让用户确认新增项。
3. **非确定性**：两轮评测输出不同但均达标（temperature 0.3）。对"每次 replan 结果可复现"有要求的场景需固定种子或缓存。
4. **并发**：重复触发 replan 无锁，revision 会叠加；UI 已有 busy 防抖，MVP 可接受。

## 6. 结论

1. **Planner 可用**：10/10 结构达标，拆解顺序、优先级、估时均合理
2. **Replanner 有效**：延期场景真实压缩并聚焦核心，容量约束生效；已完成任务保留由路由保证
3. **问题**：4 个已修复（错误信息、幻觉任务、去重、容量约束），4 个遗留观察记录在案
4. **达到进入 Phase 2 的标准**：核心闭环在真实 LLM 下稳定、结构合规、边界安全
